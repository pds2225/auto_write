# bizdoc-hub — 지원사업 문서 단일 진입점 (허브 오케스트레이터)

> 스킬이 많아 헷갈리는 문제의 해법(2026-07-05 사용자 확정): **입구 1개 + 자동 라우팅**.
> 기존 스킬은 그대로 두고(직접 호출도 가능), 허브는 "골라주고 이어주는" 역할만 한다.

## 라우팅 절차

1. **입력 파악**: 사용자가 준 것(공고문? 빈 양식? 완성본? 아무것도 없음?)과
   파일 형식(.hwp/.hwpx/.docx)을 확인한다. 경로는 광역 탐색 금지 — 없으면 물어본다.
2. **의도 분류** → 아래 라우팅표의 단계로 배정한다. 모호하면 **질문 1개**로 확정
   (예: "공고 분석이 먼저인가요, 바로 작성인가요?").
3. **해당 스킬/도구 실행** → 끝나면 **다음 단계를 제안**한다(연계 흐름 참조).
4. 여러 단계를 한 번에 요청받으면(예: "공고부터 제출까지") 연계 흐름 순서로
   순차 실행하고, 단계마다 산출물을 보고한다.

## 라우팅표 (의도 → 담당)

| 의도(사용자 말) | 담당 | DOCX | HWPX |
|---|---|:--:|:--:|
| 공고·양식 분석, 자격·마감·평가기준, "어디 지원?" (+📞고객사 확인 항목) | 스킬 `announcement-form-analysis` | ✅ | ✅(텍스트 추출) |
| 처음부터 사업계획서 **내용(본문) 작성** (PSST 서술) | 스킬 `bizplan-orchestrator` | ✅(md→이식) | md→이식 |
| 완성본 A → 빈 양식 B **사실 전사**(글 새로 안 씀) | 스킬 `cross-form-submission` | ✅ | ⚠ DOCX 경유 |
| 원본 양식에 **기업정보 직접 채움**(변환 없이) | CLI `py -3.11 app\hwp_fill_direct.py` | — | ✅ |
| **채움+검수+제출 판정 한 번에** (fail 시 _DRAFT 강제) | CLI `py -3.11 app\hwpx_submit.py 양식.hwpx -o 결과.hwpx --identity identity.json` (exit 0/1/2/3) | — | ✅ |
| 완성 DOCX **다듬기·품질점수**(서식·안내문구·강조) | 스킬 `document-quality-orchestrator` (별칭 커맨드: /improve-doc-quality = /auto-write-quality) | ✅ | 게이트만(hwpx_submit) |
| HWP/HWPX ↔ DOCX **변환** | 스킬 `docx-hwp-conversion` | ✅ | ✅ |
| 제출 가능성 **진단만**(읽기전용) | CLI `py -3.11 app\self_diagnose.py`(DOCX) / `hwpx_submit.py`(HWPX) | ✅ | ✅ |

- ✅=완성 경로 · ⚠=우회 경로 · —=해당 없음. HWPX 열은 2026-07-05 PR #60 기준.
- 서술 본문 작성과 사실 전사는 다르다: **내용을 새로 쓰면 bizplan, 있는 값을 옮기면
  cross-form/채움**. 헷갈리면 "새 문장을 만들어야 하나?"로 판별.

## 연계 흐름 (전체 파이프라인)

```
공고·양식 분석 ─→ bizplan(본문 작성) ─→ 값 채움(기업정보) ─→ 품질/검수 게이트 ─→ 제출본
(무엇을 쓸지)     (서술 내용)          (사실값·체크박스)     (fail=_DRAFT)      (한글 확인)
```
- 각 단계 산출물이 다음 단계 입력. 건너뛰기 가능(예: 내용 다 있으면 채움부터).
- 이미지: 직접 생성 금지 — NotebookLM 프롬프트 삽입(내용만, 디자인 지시 제외).

## 불변 원칙 (모든 단계 공통)

원본 미수정 · 날조 0 · 오매칭<빈칸<덮어쓰기 · fail 시 _DRAFT(제출 차단) ·
경로는 사용자에게 질문(광역 스캔 금지) · 테스트는 `py -3.11`.

## 경계

- 개별 스킬을 정확히 지목한 요청 → 그 스킬 직접(허브 생략).
- 쇼핑·업무관제·웹개발 등 문서 외 도메인 → 이 허브 대상 아님.
