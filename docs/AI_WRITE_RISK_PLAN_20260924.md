# AutoWrite 예상 문제와 사전 해결 계획

작성 기준: 2026-09-24 / 대상: 빈 HWP·HWPX 양식 + 공고문 + 사실 본문으로 기존 웹에서 작성하는 기능

**우선순위 결론: 지원 범위와 시험자료를 확정하고 → 원본 변환·재열기·렌더를 먼저 증명하고 → 정확한 작성 위치와 양식 보존을 검증한 뒤 → 근거 기반 AI 작성·도식·자동 보정을 연결한다.** 글을 먼저 잘 쓰게 만든 뒤 파일 문제를 해결하는 순서는 재작업 위험이 크다.

이 문서는 개발 인계용 위험 분석·실행 순서 제안이다. 개발 완료 보고가 아니며 개발 상태 정본인 GitHub `origin/main:TASK.md`를 대체하지 않는다. 이번 요청에서는 기존 시트와 코드를 확인하고 계획 문서를 작성했다. 시트·제품 코드는 수정하지 않았고 새로운 제품 시험도 실행하지 않았다.

## 사전에 해결하면 가장 효과적인 순서

‘사전 해결’은 모든 기능을 먼저 만든다는 뜻이 아니다. 값싼 계약 확정과 짧은 실제 실험으로, 이후 설계를 바꾸게 할 불확실성을 먼저 제거한다. 아래 단계가 실패해도 이미 확보한 입력과 초안은 보존하며, 원인과 무관한 작업은 병행할 수 있다. 선행조건을 통과하지 않은 결과를 FINAL로 승격하지 않는다.

**기존 7개 작업 ID는 유지한다.** AW-HWP-006-A/B는 기존 006의 사전 실험/최종 연동 구분이며 별도 Epic이 아니다. 현재 순서 `001→002→003→004→006→005→007`을 그대로 실행하기보다 `001+006-A→002+004 최소시험→003→004+006-B→005→007`로 바꾸는 제안이다. 초기 004 최소시험은 AI 품질 구현이 아니라 제공 텍스트의 안전한 삽입 검증이다.

단계 1의 정답표·사실 기준 정리는 단계 2의 엔진 실험과 병행할 수 있다. 단계 3 이후의 본문/도식 개발은 변환·렌더·보호영역 계약이 정해진 뒤 진행한다. 화면의 상세 개선과 범용 양식 확대는 하나의 실제 세 입력 흐름이 통과한 다음으로 둔다.

## 다른 AI에게도 동일하게 전달할 구현 계약

새로운 범용 엔진을 별도로 만들지 않고 기존 `TemplateProfile`, `DocumentPlan`, `StageResult`, `ArtifactBundle`, 작성·채움·이미지·검수 경로를 확장한다. 아래는 필요한 정보의 의미이며 별도 데이터베이스나 프레임워크 도입 지시가 아니다.

| 계약 | 반드시 남길 정보 | 불변조건 |
|---|---|---|
| 입력 묶음 | project/run, 양식·공고·본문의 역할과 hash, 원본 경로, 코드/모델/설정 버전 | 원본 불변. 다른 프로젝트 자료를 자동 혼입하지 않음. 본문 hash도 포함. |
| 작성영역 | 양식 revision/hash, 섹션·중첩 표 경로·셀/문단 ID, 보호구조, 허용 편집, 적용 공고조건 | 보호영역에는 쓰지 않음. 반복 라벨만으로 위치를 확정하지 않음. 구조가 바뀌면 낡은 앵커 무효. |
| 사실 | fact ID, 값·단위·기간·대상, 출처 위치, ACTUAL/IN_PROGRESS/TARGET/ASSUMPTION/VERIFY/DEPRECATED, 계산식 | 명확한 TARGET/ASSUMPTION은 그 상태만으로 실패하지 않음. 미제공과 N/A는 사실 상태와 별도로 구분. |
| 작성 계획 | region ID, 사용할 fact ID, 문장·표·도식, 적용 조건, 필수 사실, 미반영 원문/이유 | AI가 편집 위치나 사실을 임의로 늘리지 않음. 본문의 모든 단어를 억지로 사용해야 한다는 뜻은 아님. |
| 검수·산출물 | candidate hash, 렌더 원본 hash, 재열기 엔진/버전/결과, 전체 page 목록, 페이지별 판정·근거, PDF hash, 다운로드 hash | 생성/구조통과/재열기통과/시각통과는 별개. 검사 중 후보 변경 시 증거 무효. |
| 재실행 | correction attempt, 단계별 완료/실패, user edit revision, 최종 확정 revision, 오류 위치/사유 | 최초 초안 이후 추가 보정 최대 3회. 별도 재시도 루프가 이 제한을 우회하지 않음. |

제안하는 FINAL 판정은 다음 조건의 **동시 충족**이다. 통과하지 못했다고 해서 작성 가능한 초안을 숨기지는 않는다.

1. 적용되는 필수 공고조건과 필수 작성내용 충족. 비적용에는 근거 있는 N/A, 미확인은 UNKNOWN으로 기록.
2. 핵심 사실의 근거·상태·동일 KPI 일관성 확인. 계산값에 필요한 산식 확정.
3. 원본 불변, 보호영역 보존, 유효한 HWPX 구조와 실제 최종 파일 재열기 성공.
4. 최신 후보 자체로 전체 페이지를 렌더하고 검수 완료. 구조 검사나 PDF 생성 성공만으로 대체 불가.
5. 현재 명세가 요구하는 실제 한글 호환성 증거 확보. 독립 렌더러의 성공을 자동으로 동등한 증거로 취급하지 않음.
6. 요청/공고가 요구하는 HWP가 있으면 실제 HWP 변환·재열기 검증. HWP 미선택 자체는 실패 아님.
7. 웹 다운로드 파일이 검수한 후보와 동일하고, 생성 이후 변경된 후보의 낡은 검수 결과가 남지 않음.

지원 환경이 없어 검수가 미실행이면 DRAFT/REVIEW_REQUIRED로 이유를 표시한다. 미실행은 실패의 원인과 구분해 기록하되 최종 제출 판정에서는 통과로 세지 않는다.

## 첫 실행 단위와 증거

첫 실행은 **AI 본문 품질 개발이 아니라 ‘실제 양식 하나에서 안전하게 쓰고 열 수 있는가’의 확인**으로 한정한다.

- 입력: 출처가 확인된 빈 HWP와 HWPX, 각 공고, 충분한 사실 본문. 같은 양식의 두 형식이면 변환 시험에는 쓸 수 있으나 독립 양식 일반화 증거로 중복 집계하지 않는다.
- 동작: 읽기 전용 원본 기록 → HWP의 검증된 작업본 변환 → 작성영역/보호영역 추출 → 확정 텍스트 한 문단·내용 표·설명도식을 허용 위치에 삽입 → 최종 HWPX 재열기 → 전체 렌더 → 페이지 검수.
- 실패 변형: 렌더러 없음, 손상 입력, 중복 라벨, 긴 문장, 기존 그림 없음, 후속 섹션, 렌더 이후 파일 변경, 미제공 필수 사실.
- 증거: 입력 manifest, 보호영역 diff, 작성 위치/미반영 목록, 재열기 결과, 최종 후보/PDF hash, 페이지별 검사표, 오류별 DRAFT 판정.
- 통과 시: AW-HWP-003의 본문 생성 범위를 확대. 실패 시: 실패 위치의 어댑터·앵커·렌더만 수정하고 같은 시험을 다시 수행.

TP-01~10은 그대로 유지하고 AT-004/010/012/014/016에 동시 실행·재시작·입력 제한·다운로드 동일성 등의 하위 시나리오를 추가하는 방식을 권한다. 개발 상태는 TASK에서, 시험 결과는 AT별 증거에서, 개별 생성 문서 상태는 실행 리포트에서 관리한다.

문서 품질점수는 미측정이며 이번 작업의 성격상 부여하지 않았다. 수정한 원본은 없으므로 원본 백업은 새로 만들지 않았다. 남은 일은 이 계획에 따른 실제 시험자료 확보와 단계별 구현·실증이다.
