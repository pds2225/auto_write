# bizplan-orchestrator — 사업계획서 본문 작성

## 실행 환경 (Grok Bot에서 실행할 때)
- 이 스킬에 나오는 `D:\…`, `C:\Users\ekth3\…`, `바탕 화면\…` 경로와 `py -3.11` / `python` / `pwsh` 명령은 다솜님 Windows 노트북 기준이다. Shell·Read에 machineId `b09d5493-c6d4-4760-b6fa-a855d89774e9` 를 넣어 노트북에서 PowerShell로 실행·읽기 한다. 큰 파일이나 바이너리는 CopyToBox로 박스에 가져와 처리하고, 결과물을 노트북에 둬야 하면 CopyFromBox로 돌려놓는다. 노트북이 연결돼 있지 않으면(ListMachines로 확인) 그렇게 알리고 멈춘다.
- 원본 파일은 절대 덮어쓰지 않는다(새 파일로 저장). 삭제·이동·메일 발송·제출 같은 되돌릴 수 없는 일은 사용자가 그 자리에서 분명히 승인했을 때만 한다.
- 원문에 남아 있는 Codex 전용 요소(슬래시 커맨드 `/…`, `.Codex/agents/*` 에이전트, `Agent(...)` 호출, `model: "opus"`, 훅, AGENTS.md 자동주입)는 여기 없다. 슬래시 커맨드는 같은 CLI를 직접 실행하거나 노트북의 `<프로젝트>\.Codex\commands\<이름>.md` 를 읽어 그 절차를 따른다. 에이전트 이름은 '단계/역할'로 읽고 직접 순서대로 수행한다(작성과 검수를 분리해야 하면 검수만 서브에이전트에 맡긴다). 에이전트 정의가 필요하면 `<프로젝트>\.Codex\agents\<이름>.md` 또는 `C:\Users\ekth3\.Codex\agents\<이름>.md` 를 읽는다.
- `docs/…`, `app/…` 같은 상대경로는 해당 프로젝트 폴더(예: `D:\auto_write\docs\…`) 기준이다. `.omc/wiki` 위키는 노트북 `D:\.omc\wiki` 에 있다.
- 다른 스킬 이름(예: `cross-form-submission`)은 Grok Bot 스킬 id와 같다.


> bizdoc-hub 가 가리키는 **작성 단계** 스킬.
> 구현 본체는 기존 CLI·커맨드에 있다(이 스킬은 라우팅·경계만 고정).

## 실행

```powershell
cd D:\auto_write\app
py -3.11 bizplan_autopilot.py "<초안.docx>" --brief-file 브리프.txt --announcement-file 공고.txt
# 기본 산출: 입력 원본 폴더\{지원사업명}_{문서종류}_{MMDDHH} vN.hwpx  (워드가 필요하면 -o out.docx)
# 또는 Codex 커맨드: /auto-write-bizplan
```

상세 옵션·안전 원칙: 노트북 `D:\auto_write\.Codex\commands\auto-write-bizplan.md` 를 Read(machineId)로 읽는다.

## 파이프라인 (요약)

1. AI 본문 작성/보강 — PSST 약점 영역. 무출처 수치는 `[확인필요]` (날조 0).
2. 품질 오토파일럿 — 서식 + 이미지(NotebookLM 프롬프트) + PSST 가이드 + 점수 게이트.
3. 공고 채점 — 목표 충족률까지 약점 보완 루프.
4. 수용검사 — fail 시 출력명 `_DRAFT` 강제.

# (방법 B) 처음부터 직접 작성하는 절차 — 노트북 CLI를 못 쓰거나 빈 문서에서 시작할 때

> 아래는 이전 전역 버전의 상세 절차다. planner/writer/reviewer는 별도 에이전트가 아니라 단계 이름이다. 작성과 검수는 분리한다: 검수(reviewer) 단계는 가능하면 서브에이전트에 맡겨 자기 글을 스스로 통과시키지 않게 한다. 산출 `_bizplan/` 폴더는 노트북 작업폴더 또는 박스 /workspace 에 둔다. 최종 제출본이 필요하면 위 방법 A(한글 HWPX 기본) 또는 `docx-hwp-conversion` 으로 이어간다.



**실행 모드:** 순차 서브에이전트 파이프라인 (수집·설계 → 작성 → 검증 → 보완 루프)

> 빈 문서에서 시작해 **사업 정보 정리 → 목차를 평가기준에 매핑 → PSST 본문 작성 →
> 자가검증·점수 → 보완**까지 한 번에 끝낸다. 이미 있는 문서를 다듬는 게 아니라
> **처음부터 작성**하는 것이 이 하네스의 역할이다.

## 1. 에이전트 구성

| 에이전트 | 파일 | 역할 | 단계 | 모델 |
|---------|------|------|------|------|
| bizplan-planner | `.Codex/agents/bizplan-planner.md` | 사업 정보 수집·정리 + 목차를 평가기준에 매핑(골격 설계) | Phase 1 | opus |
| bizplan-writer | `.Codex/agents/bizplan-writer.md` | PSST 구조로 각 섹션 본문 작성 | Phase 2 | opus |
| bizplan-reviewer | `.Codex/agents/bizplan-reviewer.md` | 평가기준 부합·PSST 충실도·정량근거·논리 자가검증 + 점수·보완점 | Phase 3 | opus |

**모든 Agent 호출 시 `model: "opus"` 파라미터를 명시한다.**

쉽게 말하면 — 한 명(planner)이 "무엇을 어떤 순서로 쓸지" 뼈대를 짜고, 한 명(writer)이
그 뼈대에 살(본문)을 붙이고, 마지막 한 명(reviewer)이 "심사위원 눈으로" 점검해 점수를
매기고 고칠 곳을 짚어준다.

모든 산출물은 **실행 폴더의 상대경로 `_bizplan/`** 아래에 저장한다. 절대경로 하드코딩 금지.

| 파일 | 만드는 단계 | 내용 |
|------|-----------|------|
| `_bizplan/01_outline.md` | Phase 1 (planner) | 사업 정보 정리 + 목차 ↔ 평가기준 매핑(골격) |

## 3. Phase 0: 컨텍스트 확인

작업 시작 전 아래를 먼저 확인해 실행 모드를 정한다. (토큰 절약 — 전체 탐색 금지, 필요한 것만)

1. **사업 정보 확보 여부** — 사용자가 준 정보로 사업 아이템·고객·문제·해결책·매출모델·팀이
   파악되는가? 핵심이 비면 **그 항목만** 1~5개 질문으로 모은다(되묻기 최소화).
2. **지원사업 맥락** — 어느 사업(예비창업패키지·초기창업패키지·R&D·투자IR 등)인지,
   평가기준·양식·분량 제한이 있는지 확인한다.
   - 공고문/양식 파일이 있으면 → **announcement-form-analysis 스킬로 먼저 분석**하라고
     안내하거나, 이미 분석 결과(요구·평가기준)가 있으면 그것을 planner 입력으로 넘긴다.
3. **기존 산출물 확인** — `_bizplan/` 안에 01/02/03 이 있는지 본다.

| 조건 | 실행 모드 | 동작 |
|------|----------|------|
| `_bizplan/` 미존재 | **초기 실행** | Phase 1부터 전체 수행 |
| `01_outline.md` 있고 사용자 "이어서/계속/다음" | **이어서 실행** | 마지막 완료 단계 다음부터 |
| 사용자가 "○○ 섹션만 다시" / "검증만 다시" | **부분 재실행** | [10절](#10-부분-재실행-규칙) 참조 |

핵심 정보가 비었는데 추측으로 진행하지 않는다. 단, 사용자가 "알아서/대충 채워서" 라고 하면
합리적 가정을 명시(가정으로 표시)하고 진행한다.

## 4. Phase 1: 정보수집·목차 설계 (bizplan-planner)

`역할 `bizplan-planner` 단계(직접 수행, 필요 시 서브에이전트 위임)` 호출.

- **입력으로 넘길 것:** 사용자가 준 사업 정보, 지원사업 맥락(평가기준·양식·분량),
  (있으면) announcement-form-analysis 결과, `_bizplan/` 경로.
- **planner가 할 일:**
  1. 사업 정보를 PSST 4영역(문제인식·해결방안·성장전략·팀)으로 분류·정리.
  2. 제출 양식/평가기준이 있으면 **목차 각 항목을 평가배점에 매핑**(어느 항목이 몇 점짜리인지).
  3. 빈 칸(근거·수치·실적 부족분)을 표시해 writer가 채울 지점을 명확히.
- **산출:** `_bizplan/01_outline.md`
- 정보가 결정적으로 부족하면 planner가 **추가 질문 목록**을 outline 상단에 남기고,
  오케스트레이터는 그 질문을 사용자에게 전달한다(추측 금지).

## 5. Phase 2: 초안 작성 (bizplan-writer)

`역할 `bizplan-writer` 단계(직접 수행, 필요 시 서브에이전트 위임)` 호출.

- **입력:** `_bizplan/01_outline.md` (반드시 먼저 읽게 함), 평가기준·분량 제한.
- **writer가 할 일:** outline 골격을 따라 **PSST 구조로 각 섹션 본문**을 작성.
  - Problem(문제인식): 시장·고객의 페인, 규모·근거 수치.
  - Solution(해결방안): 제품/서비스, 차별성, 실현 가능성, 개발 현황.
  - Scale-up(성장전략): 시장진입·매출계획·자금사용·로드맵.
  - Team(팀): 대표·팀 역량, 보유자원, 외부협력.
  - 정량근거(숫자·출처)를 본문에 녹이고, 빈 수치는 `[확인필요]` 로 표시(거짓 수치 금지).
- **산출:** `_bizplan/02_draft.md`

---

## 6. Phase 3: 자가검증 (bizplan-reviewer)

`역할 `bizplan-reviewer` 단계(직접 수행, 필요 시 서브에이전트 위임)` 호출.

- **입력:** `_bizplan/02_draft.md` + `_bizplan/01_outline.md`(평가기준 매핑) 둘 다 읽게 함.
- **reviewer가 할 일(심사위원 관점):**
  1. **평가기준 부합** — 각 평가항목이 본문에서 충분히 다뤄졌는지 항목별 체크.
  2. **PSST 충실도** — 4영역이 균형 있고 논리적으로 연결되는지.
  3. **정량근거** — 주장에 숫자·출처가 붙었는지, `[확인필요]` 잔존 여부.
  4. **논리·일관성** — 문제↔해결↔성장↔팀이 한 줄기로 이어지는지.
  - **항목별 점수 + 종합점수 + 우선순위 보완점** 을 남긴다.
- **산출:** `_bizplan/03_review.md`

> 작성(writer)과 검증(reviewer)은 반드시 **분리된 단계**다. writer가 자기 글을 자가승인하지
> 않는다 — 검증은 별도 에이전트가 한다.

---

## 7. Phase 4: 보완 루프

reviewer 점수가 기준(기본 **종합 80점/100**) 미만이거나 우선순위 보완점이 남으면:

1. 오케스트레이터가 **03_review.md의 보완점**을 정리해 다시 `bizplan-writer` 에 넘긴다.
2. writer가 해당 섹션만 고쳐 `02_draft.md`(또는 `04_final.md`)를 갱신.
3. 다시 `bizplan-reviewer` 로 재검증.
4. 기준 통과 또는 **최대 2회 반복** 후 종료(무한 루프 방지). 미달이면 남은 약점을 사용자에게 보고.

`[확인필요]` 로 표시된 수치가 남아 있으면 통과 처리하지 말고, 그 목록을 사용자에게 질문한다.

---

## 8. Phase 5: 산출 및 보고

1. 보완 반영본을 `_bizplan/04_final.md` 로 저장(루프가 없었으면 `02_draft.md`가 최종).
2. **DOCX/HWP 변환 안내** (이 하네스는 md 까지 — 사용자가 원하면):
   - 다듬기·서식·안내문구 정리·품질점수가 필요하면 → **document-quality-orchestrator 스킬**로 연계.
   - 단순 md→docx 변환만 필요하면 PowerShell 안내:
     `python -m pip install python-docx` 후 변환 스크립트, 또는 Pandoc:
     `pandoc _bizplan\04_final.md -o _bizplan\사업계획서.docx`
3. **사용자 보고** — 작성한 섹션, reviewer 종합점수, 남은 `[확인필요]`/약점, 다음 단계(다듬기/변환).

## 9. 데이터 전달 프로토콜

- 단계 간 전달은 **파일 기반**(`_bizplan/*.md` 상대경로). 에이전트는 직전 산출 파일을 먼저 읽는다.
- 오케스트레이터는 각 Agent 호출 시 **읽어야 할 입력 파일 경로**와 **써야 할 출력 파일 경로**를
  프롬프트에 명시한다.
- 사업 핵심 수치·평가기준은 outline 상단에 모아두어 writer/reviewer가 동일 기준을 공유하게 한다.

## 10. 부분 재실행 규칙

| 사용자 요청 | 실행 |
|------------|------|

## 11. 에러 핸들링

- **정보 부족:** planner가 추측으로 채우지 않고 질문 목록을 남긴다 → 사용자에게 전달.
- **거짓 수치 위험:** 확인 안 된 숫자는 만들어내지 말고 `[확인필요]` 표시. reviewer가 잔존 여부 체크.
- **평가기준 미확보:** 양식/공고가 없으면 일반 PSST 표준 목차로 작성하되, "공고 분석(announcement-form-analysis)
  을 먼저 하면 정확도가 올라간다"고 안내.
- **보완 루프 미수렴:** 최대 2회 후 중단하고 남은 약점을 사용자에게 솔직히 보고(완료처럼 말하지 않음).
- **Agent 실패/빈 산출:** 해당 Phase 1회 재시도, 그래도 실패하면 어느 단계에서 막혔는지 보고.
- **경계 침범 감지:** 사용자가 "이미 있는 문서 다듬어줘/서식 정리/품질점수"를 원하면 이 스킬이 아니라
  document-quality-orchestrator 를, "공고/양식 분석"이면 announcement-form-analysis 를 안내·연계.

## 12. 오케스트레이터 자기 검증

작업 종료 전 아래를 모두 만족하는지 점검한다.

- [ ] Phase 0에서 사업 정보·지원사업 맥락·기존 `_bizplan/` 산출물을 확인했다.
- [ ] 산출물을 **상대경로 `_bizplan/`** 에 저장했다(절대경로 하드코딩 없음).
- [ ] 흐름 순서를 지켰다: planner(01) → writer(02) → reviewer(03) → 보완 → 산출.
- [ ] 작성(writer)과 검증(reviewer)을 **분리된 에이전트**로 수행했다(자가승인 금지).
- [ ] reviewer 종합점수·보완점을 기록했고, 기준 미달이면 보완 루프를 돌렸다(최대 2회).
- [ ] `[확인필요]` 수치를 임의로 지어내지 않았고, 남은 항목을 사용자에게 질문했다.
- [ ] 부분 재실행 시 요청 범위 외 산출물을 건드리지 않았다.
- [ ] 최종 보고에 점수·남은 약점·다음 단계(다듬기/변환)를 포함했다.
- [ ] 경계(다듬기=DQO / 분석=공고분석)를 넘지 않았고, 필요 시 올바른 스킬로 안내했다.
